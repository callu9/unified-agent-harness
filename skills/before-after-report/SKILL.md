# 변경 전후 비교 보고서

실제 검증 근거를 바탕으로 변경의 효과, 확인한 범위, 남은 작업을 보고한다.

## 기준 확인

- 현재 사용자 요청과 대상 프로젝트 지침에 따라 저장 위치, 파일 이름, 버전, 담당 명칭을 확인한다. 기존 보고서를 고칠 때는 관련 카드와 요약만 맞추고 다른 항목과 근거 링크는 보존한다.
- 검증 실행, 배포·머지, 이슈·PR 작성, 다른 문서 반영, 외부 전달은 각각 현재 요청에 포함된 범위에서만 한다. 보고서 작성 요청은 다른 작업의 실행 권한을 주지 않는다.
- 이슈의 기존 판정, 최신 코드·PR·배포 기록, 직접 확인한 화면·API·데이터 근거를 대조한다. 근거가 충돌하면 확인한 시각·환경·범위를 함께 적는다.

## 보고서 구조

1. **한눈에 보기.** 이슈, 확인된 문제와 수정 효과, 현재 검증·배포 상태, 영향 분류를 짧게 적는다. 각 항목은 상세 카드 앵커로 연결한다. 진척과 변경 전후는 열을 나누고, 필요하면 표를 나눈다.
2. **영향 분류.** 변경이 사용 시나리오(시연·운영 경로 등 기준이 되는 흐름)에 미치는 영향을 `영향 있음`, `조건부 영향`, `영향 없음`, `미확인`으로 표시하고 이유나 발동 조건을 적는다. 기준 시나리오가 주어지면 단계와 확인 경로를 인용하고, 근거가 부족하면 `미확인`으로 남긴다.
3. **이슈별 상세.** 카드마다 `문제 / 왜 문제인가 / 수정`을 쓴다. 수정이 확정되지 않았으면 `수정 방향`으로 표시한다. 비교표에는 같은 항목의 BEFORE, AFTER와 근거 환경을 넣는다. 검증한 화면은 같은 영역을 확대한 크롭을 나란히 두고 `전체 화면·추가 캡처 보기`에서 원본과 추가 근거를 열 수 있게 한다.

- 상세 카드는 열고 닫을 수 있게 한다. 판단이 남은 카드(배포 판단, 기준 합의 등)는 기본으로 열고, 검증이 끝난 카드는 기본으로 접는다.
- `한눈에 보기`와 `기준 합의 필요`의 각 행을 누르면 해당 상세 카드가 열리고 대상 위치로 이동하게 한다. 키보드로 이동할 수 있는 링크를 두고, PR·근거 링크는 각자의 목적지로 연결한다.

새 HTML의 마크업이 필요하면 [이슈 카드 예시](assets/issue-card.html)의 제목, 비교표와 근거 접기 구조를 참고한다. 기존 HTML의 컴포넌트와 서식이 있으면 그 규칙을 따른다.

## 비교 근거

- 실제로 있는 근거만 요구하고 쓴다. 화면 캡처가 없는 API·로컬 전용 앱은 요청·응답 로그나 로컬 재현 결과를 근거로 삼을 수 있다.
- 같은 작업·화면·입력값·단위·조건인지 있는 근거(캡처·API·로그)를 대조한다. 실험에서 의도적으로 바꾼 변수와 고정한 조건을 적는다. 조건이 다른 캡처는 각각의 관측으로만 소개한다.
- 반영 전에 캡처가 있는 보고서는 원본과 크롭을 직접 열어, 캡처가 없는 보고서는 인용한 로그·응답·재현 결과 파일을 직접 열어 필드, 값, 단위, 오류 문구, 버튼 상태를 읽고 캡션·비교표와 하나씩 대조한다. API·데이터 원본 정밀도와 반올림·절삭이 적용된 화면 표기는 함께 표시한다.
- 수정 전 실제 환경의 원본이 없으면 확보한 출처를 해당 컷에 붙인다. 예: `수정 전 커밋의 로컬 재현`, `테스트 대역 사용`, `API 응답만 확보`, `수정 전 근거 미확보`. 재현과 실제 환경 관측을 구분하고, 대역으로 검증한 경로를 실제 저장·연산 결과로 해석하지 않는다.
- 설명에 필요한 근거만 연결한다. 이슈·PR URL과 대상 브랜치는 있을 때만 적고, 필요하면 배포 성공 기록·커밋, 검증일·환경·작업 ID·요청 ID를 포함한다. 캡처와 근거 파일의 불필요한 식별자나 민감정보는 공유 범위에 맞게 가린다.

## 상태와 담당

| 상태 | 기록할 근거 |
| --- | --- |
| 로컬 검증 완료 (배포 없음) | 로컬 빌드나 대역에서 확인한 범위만. 배포·PR이 없는 작업은 여기까지 |
| 로컬 검증 완료 · 배포 대기 | 로컬 빌드나 대역에서 확인한 범위, PR이 있으면 Draft·리뷰·머지 상태와 대상 브랜치 |
| 배포 완료 · 검증 대기 | 대상 커밋과 배포 성공 증거, 확인이 필요한 화면·API |
| 배포·검증 완료 | 배포된 커밋과 실제 환경에서 재확인한 절차·결과 |
| 일부 반영 또는 미확인 | 반영된 API·화면과 대기 중인 경로, 다음 확인 조건 |

기술 상태(Draft 여부·머지·배포 등 있는 것만)와 검증 상태는 각각 표시한다. 영향 분류는 기술 상태와 별도 열에 둔다.

배포 검증 결과를 작업 추적 문서와 HTML에 함께 반영할 때는 두 문서의 상태를 같이 갱신한다. 배포 PR·실행 기록과 실제 검증 결과를 연결하고, 재현에 필요한 작업 ID와 요청 ID를 기록한다. 기존 캡처는 촬영 당시 환경을 유지해 표기한다.

담당은 원인 영역별로 나누고, 각 담당에 재현 입력과 확인 질문을 적는다.

- FE 표시·입력·상태 결함, BE 저장·조회·응답 결함: 확인된 결함과 수정 근거를 해당 담당에 기록한다.
- 정책이나 제품 계약을 정해야 할 때: 결정할 질문과 가능한 기준을 적는다. 의도된 동작이나 입력 기대 동작은 근거와 전제를 기록한다.
- 모델 계산, 결과값 타당성, 데이터·전처리 검증: 재현 입력과 확인 질문을 해당 담당에 연결한다.
- 같은 현상에 여러 영역의 원인이 있으면 원인·담당·확인 작업을 영역별로 분리한다.

## 제출 전 확인

저장한 HTML을 다시 열어 상세 앵커, 상대 경로, PR·근거 링크, 캡처가 있으면 전체 화면과 크롭(없으면 인용한 로그·응답·재현 결과 파일), 좁은 화면에서의 읽기 순서를 확인한다. 기본 열림·접힘, 행 클릭과 키보드 링크 이동, 상세 링크를 직접 열었을 때 대상 카드가 펼쳐지는지도 확인한다. 확인한 상태와 수정하지 않은 관련 업무의 상태를 혼동하지 않도록 실제 변경 범위를 최종 답변에 적는다.
